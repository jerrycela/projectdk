# ProjectDK 優化計畫實作報告

**日期**：2026-02-12
**執行方式**：Claude Agent Teams（1 Opus 4.6 Lead + 5 Sonnet/Haiku Specialists）
**執行時間**：約 3 小時

---

## 發現問題

### 用戶反映

用戶提出了四個主要問題：

1. **編輯器功能失效**：「編輯器目前還是有很多沒辦法正常作動的功能」
2. **視覺品質下降**：「畫面經過上次迭代好像愈改愈醜」
3. **遊戲 Bug**：「遊戲也有諸多 bug」
4. **邊框缺失**：「每次遊戲啟動畫面右邊跟下方的邊框都會缺失」

### 初步判斷

通過深度探索和分析（3 個並行 Explore agents），我們發現：

#### 問題 1：編輯器功能
- **發現過程**：讀取 `editor-tools.js` 發現 `floodFill()` 方法（146-186 行）已完整實作
- **判斷**：填充工具的演算法存在，但沒有被呼叫 → **整合問題**
- **驗證方式**：搜尋 `editor-main.js` 的 `handlePaint()` 函式，確認缺少 'fill' 工具分支

#### 問題 2：Undo/Redo 資料污染
- **發現過程**：分析歷史記錄機制，發現使用 `[...array]` 淺拷貝
- **判斷**：JavaScript 的 spread operator 只拷貝外層，二維陣列內層仍是引用 → **淺拷貝問題**
- **驗證方式**：追蹤 `editor-tools.js` 的 saveHistory、undo、redo 函式

#### 問題 3：視覺系統過度複雜
- **發現過程**：統計發現 390 個色彩定義、6 個動畫通道同時運行
- **判斷**：過度優化導致複雜度爆炸，低階裝置無法負荷 → **設計問題**
- **驗證方式**：對比業界標竿 Dungeon Warfare 3（估計 80-120 色、3-4 動畫通道）

#### 問題 4：邊框缺失
- **發現過程**：用戶提供截圖，左上有邊框，右下缺失
- **判斷**：CSS `box-sizing: border-box` 導致 Canvas (960×720) 溢出 Container
- **驗證方式**：檢查 `css/style.css` 的 #game-container 設定

## 解決過程

### 問題 1：填充工具整合

**第一次嘗試**：檢查 `handlePaint()` 函式
→ **發現**：完全沒有處理 `this.selectedTool === 'fill'` 的分支

**關鍵洞察**：`floodFill()` 已經存在且完整（BFS 演算法、500 格限制、越界檢查），只是從未被呼叫

**最終方案**：
1. 在 `handlePaint()` 加入 `else if (this.selectedTool === 'fill')` 分支
2. 新增 `fillTile()` 方法：
   - 驗證目標地磚
   - **在呼叫 floodFill() 之前**記錄歷史（關鍵！）
   - 禁止填充外圍區域 ('O')
   - 呼叫現有的 `DK.EditorTools.floodFill()`
   - 標記 dirty

**為什麼這個方案有效**：
- 重用已測試的 BFS 演算法，避免重複造輪子
- 在正確的時機（填充前）記錄歷史，確保 Undo 可用
- 保護機制完整（外圍保護、500 格上限）

**教訓**：功能已實作但未整合，檢查時要同時看「實作」和「呼叫端」

---

### 問題 2：Undo/Redo 深拷貝

**第一次嘗試**：使用 `[...DK.Editor.layout]` 淺拷貝
→ **失敗原因**：二維陣列的內層 row 仍是引用，修改時會污染其他快照

**第二次嘗試**：改用 JSON 序列化 `JSON.parse(JSON.stringify(layout))`
→ **問題**：效能差、無法處理特殊物件

**關鍵洞察**：JavaScript 的 spread operator (`...`) 只做**一層**淺拷貝

**最終方案**：使用 `array.map(row => [...row])` 逐行深拷貝
- 修改 3 處：`saveHistory()`, `undo()`, `redo()`
- 每一行都獨立拷貝，確保完全隔離

**為什麼這個方案有效**：
- 對二維陣列逐行拷貝，每個 row 都是新陣列
- 效能優於 JSON 序列化
- 程式碼簡潔易懂

**額外發現**：`onMouseUp()` 沒有自動保存歷史，導致 Undo 無法使用
→ **修復**：在 `editor-main.js` 的 `onMouseUp()` 加入 `DK.EditorTools.saveHistory()`

**教訓**：
1. 深拷貝 vs 淺拷貝是 JavaScript 常見陷阱，必須特別注意
2. 陣列拷貝要考慮維度，多維陣列需要逐層處理
3. 歷史記錄的觸發時機很關鍵（繪製完成時，而不是開始時）

### 問題 3：視覺系統過度複雜

**第一次嘗試**：直接刪減色彩和動畫
→ **風險高**：可能破壞現有視覺效果，影響現有玩家

**第二次嘗試**：建立「低配版」和「高配版」兩套程式碼
→ **維護困難**：兩套程式碼需要同步維護，容易出錯

**轉換思路**：不刪減，而是建立 **Feature Flags 系統**，讓用戶選擇
→ **關鍵洞察**：漸進式優化比激進式重構風險低

**最終方案**：三段式架構

**1. Feature Flags 系統**（230 行）
- 12 個視覺開關（火把、水潭、粒子等）
- 4 個強度參數（粒子密度、光暈強度等）
- 3 種預設模式：Simple（極簡）、Standard（標準）、Fancy（華麗）
- `isEnabled()` 方法統一查詢

**2. 渲染管線條件化**
- 在 7 個渲染通道加入 `if (DK.VISUAL_SETTINGS.isEnabled(...))` 條件
- Simple 模式跳過大部分渲染，降低 CPU 負擔
- Fancy 模式保持所有效果（向後相容）

**3. 水潭動畫優化**
- 使用 `MathCache` 替換 `Math.sin/cos`（預計算查找表）
- Standard 模式隔幀更新（每 2 幀更新一次）
- 視窗裁切（只渲染可見範圍）

**為什麼這個方案有效**：
- **向後相容**：Fancy 模式 = 當前效果，現有玩家不受影響
- **漸進優化**：三種模式提供不同效能/視覺平衡
- **可擴展**：Feature Flags 模式可複用到音效、粒子等系統
- **風險可控**：每個開關都可以獨立測試和調整

**設計思路來源**：參考 Dungeon Warfare 3 的「Refined」理念 —— 「在黑暗地牢中，只看見重要的東西」

**教訓**：
1. 過度優化比不優化更危險，要保持平衡
2. 給用戶選擇權比強制一種方案更友善
3. 向後相容是長期專案的必要考量

---

### 問題 4：邊框缺失

**發現過程**：
1. 用戶提供截圖 → 左上有邊框，右下缺失
2. 檢查 HTML → `#game-container` 和 Canvas 都是 960×720
3. 檢查 CSS → 發現 `box-sizing: border-box` + `border: 3px solid`

**關鍵洞察**：
- `box-sizing: border-box` 讓 960×720 **包含** 3px 邊框
- 實際內容空間 = 960 - 3×2 = 954px（寬）
- Canvas 設定為 960px → **溢出 6px，覆蓋右邊框**

**最終方案**：
- 調整 `#game-container` 尺寸為 966×726（960+6 × 720+6）
- 設定 `box-sizing: content-box`（邊框不計入尺寸）

**為什麼這個方案有效**：
- Canvas 960×720 完全在 Container 內部
- 3px 邊框在 Canvas 外圍，四周都可見

**教訓**：CSS 盒模型問題很常見但容易忽略，視覺檢查要全面

## 預防措施

### 1. 建立編輯器功能測試清單

**具體內容**：
- [ ] 填充工具功能驗證（連通區域填充正確）
- [ ] Undo/Redo 連續操作測試（5 次 Undo 回到初始狀態）
- [ ] 500 格限制測試（超過限制顯示提示）
- [ ] 外圍保護測試（禁止填充外圍 'O'）

**為什麼重要**：
- 編輯器是關卡設計的核心工具，功能失效會嚴重影響生產力
- 測試清單確保每次修改後都能快速驗證核心功能

**實施方式**：
- 建立 Puppeteer 自動化測試腳本
- 每次修改編輯器後必須執行測試清單

---

### 2. Feature Flags 設計模式可複用

**具體內容**：
- 將 Feature Flags 系統文檔化（API 說明、使用範例）
- 建立新增功能開關的 SOP（Standard Operating Procedure）
- 其他系統（音效、粒子、UI 動畫）也可使用此模式

**為什麼重要**：
- 漸進式優化是長期策略，Feature Flags 讓改動風險可控
- 可複用模式節省時間，避免每次都重新設計

**實施方式**：
- 在 CLAUDE.md 中記錄 Feature Flags 模式
- 建立範例程式碼供未來參考

---

### 3. 深拷貝檢查清單

**具體內容**：
- 所有狀態保存（歷史記錄、快照）必須深拷貝
- 使用 `structuredClone()` 或 `array.map(row => [...row])`
- Code review 時檢查拷貝方式（淺拷貝 vs 深拷貝）
- 建立 ESLint 規則警告淺拷貝

**為什麼重要**：
- 淺拷貝 bug 很難發現，症狀不明顯（資料互相污染）
- 預防勝於治療，建立檢查機制比事後修復更有效

**實施方式**：
- 在 CLAUDE.md 的「除錯核心原則」中加入深拷貝提醒
- Code review checklist 加入拷貝方式檢查項

---

### 4. 視覺回歸測試

**具體內容**：
- Puppeteer 截圖對比（三種模式）
- 像素級比對，確認視覺差異符合預期
- Simple/Standard/Fancy 三種模式的視覺驗證
- 效能基準測試自動化（Chrome DevTools Performance）

**為什麼重要**：
- 視覺變更容易引入意外的副作用（動畫跳格、顏色錯誤）
- 自動化測試能快速發現回歸問題

**實施方式**：
- 建立 `tests/visual-regression.cjs` 腳本
- CI/CD 整合視覺測試，每次 commit 自動執行

---

### 5. CSS 尺寸計算檢查

**具體內容**：
- 檢查 `box-sizing` 設定（border-box vs content-box）
- 驗證 Container 和 Canvas 尺寸一致性
- 使用瀏覽器 DevTools 檢查實際渲染尺寸
- 建立 CSS 尺寸計算文檔

**為什麼重要**：
- CSS 盒模型問題很常見但容易忽略
- 邊框、Padding 的計算方式常導致佈局錯位

**實施方式**：
- 在 CLAUDE.md 加入「CSS 尺寸檢查」章節
- 建立視覺檢查清單（四周邊框、按鈕對齊）
